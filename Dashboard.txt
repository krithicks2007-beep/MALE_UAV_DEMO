MALE UAV AERO-PISTON ENGINE DIGITAL TWIN
DASHBOARD — FINAL DEVELOPMENT PLAN, MODULAR ARCHITECTURE & TECH STACK
======================================================================

DOCUMENT STATUS
---------------
Version: Final Dashboard Plan
Scope: Dashboard only
Target: SIH 2026 Digital Twin demonstration and progressive integration
Architecture principle: Modular, replaceable, independently testable

IMPORTANT:
This document defines the dashboard/application layer. The Digital Twin
physics model, AI/ML models, telemetry gateway, mission engine, and simulation
systems are external services/modules that the dashboard consumes.

======================================================================
0. PURPOSE
======================================================================

Build a professional, operator-facing aerospace engine-health dashboard for
the SIH 2026 Digital Twin system.

The dashboard is the primary visual interface for:

- Engine health monitoring
- Live telemetry
- Cylinder-level thermal monitoring
- Anomaly/fault visualization
- Physics-vs-actual Twin analysis
- AI/ML diagnostic output
- Degradation and RUL presentation
- Maintenance advisories
- Mission analysis and replay
- Scenario selection/injection
- Cyber-physical Twin visualization
- Alert and notification management

The dashboard must be independently developable using mock/synthetic data.

Later, the mock layer must be replaceable by the real backend, telemetry
gateway, Digital Twin Core, AI/ML services, scenario engine, mission/replay
services, and eventually real UAV data WITHOUT redesigning the dashboard UI.

======================================================================
1. CORE ARCHITECTURE PRINCIPLE
======================================================================

The dashboard follows strict separation of concerns:

                    EXTERNAL SYSTEMS
                         |
        +----------------+----------------+
        |                |                |
   Telemetry       Twin / Physics      AI / ML
   Gateway             Core            Analytics
        |                |                |
        +----------------+----------------+
                         |
                    Backend/API
                         |
                    Data Adapter
                         |
                 Application State
                         |
        +----------------+----------------+
        |                |                |
       UI             Charts          3D Twin
     Pages           /Trends        Visualization


STRICT RULES
------------

1. UI components render data and collect user interaction.
2. UI components must NOT contain physics equations.
3. UI components must NOT contain AI model logic.
4. UI components must NOT generate authoritative telemetry.
5. Scenario physics belongs outside the presentation layer.
6. Replay logic belongs outside the presentation layer.
7. The Data Adapter is the boundary between external data and UI data.
8. API/service contracts must be versioned and stable.
9. Components must be reusable and independently testable.
10. A backend or data source can be replaced without rebuilding the UI.
11. The 3D Twin renderer must be independent of the current asset source.
12. The dashboard must degrade gracefully when services are unavailable.

======================================================================
2. MODULAR ARCHITECTURE — HOW TO BUILD IT
======================================================================

The dashboard is divided into independent modules.

MODULE A — Presentation/UI
--------------------------
Responsible for:

- Pages
- Layout
- Cards
- Tables
- Buttons
- Forms
- Tabs
- Panels
- Alerts
- Status indicators

It receives already-processed data.

It does not know where the data came from.

MODULE B — Application State
----------------------------
Responsible for:

- Current telemetry
- Health state
- Alerts
- Scenario state
- Mission state
- Replay state
- Twin state
- Diagnostics state
- Connection state
- UI preferences

Recommended tool:
Zustand

MODULE C — Data Adapter
-----------------------
Responsible for translating external data into one stable dashboard model.

Possible sources:

- Mock data
- Synthetic telemetry
- REST API
- WebSocket
- Recorded telemetry
- Digital Twin Core
- AI/ML service
- Future real UAV gateway

The UI only consumes the normalized dashboard model.

MODULE D — Service/API Layer
----------------------------
Responsible for communication.

Examples:

- REST API client
- WebSocket client
- Scenario service
- Mission service
- Diagnostic service
- Replay service
- Twin service

The service layer must not be embedded inside UI components.

MODULE E — Visualization Engines
--------------------------------
Independent visualization modules:

- Telemetry chart engine
- Trend engine
- Residual visualization
- 3D Twin renderer
- Alert visualization
- Mission timeline

A visualization library can be replaced without changing the business/data
contract.

MODULE F — Domain Models / Contracts
------------------------------------
Defines stable structures for:

- Telemetry
- Health
- Diagnostics
- Alerts
- Advisory
- Mission
- Replay
- Scenario
- Twin state
- Synchronization state

These contracts are shared between frontend and backend.

MODULE G — Mock / Demo Data
---------------------------
Provides deterministic data for independent development.

Examples:

- Normal engine
- Misfire
- Injector abnormality
- Lubrication issue
- Overheating
- Sensor drift
- Abnormal vibration

Mock data must obey the same schema as real data.

MODULE H — Persistence / History
--------------------------------
Responsible for:

- Local prototype history
- Mission history
- Replay datasets
- Event history

MVP:
- In-memory
- JSON/CSV

Next stage:
- SQLite

Scalable stage:
- PostgreSQL / appropriate time-series storage

MODULE I — 3D Asset Interface
-----------------------------
Defines how the 3D Twin renderer receives an asset.

MVP:
- Procedural Three.js geometry
- Primitive engine representation

Future:
- Optimized GLB/GLTF asset
- CAD-derived asset

The renderer must not depend on Blender or SolidWorks.

6. LIVE TELEMETRY TAB
======================================================================

Display the core engine telemetry required by the project.

CORE PARAMETERS
---------------

- RPM
- MAP — Manifold Absolute Pressure
- CHT — Cylinder Head Temperature
- EGT — Exhaust Gas Temperature
- Oil Pressure
- Oil Temperature
- Fuel Flow
- Vibration
- Battery Voltage / Battery Health
- Alternator Current / Alternator Health
- Injection Timing

MULTI-CYLINDER REQUIREMENT
--------------------------

CHT and EGT must be represented at cylinder level.

Canonical structure:

cht: [C1, C2, C3, C4]
egt: [C1, C2, C3, C4]

Example:

{
  "cht": [132.4, 135.1, 133.0, 138.2],
  "egt": [815.0, 822.4, 810.2, 829.0]
}

The dashboard must not hard-code the UI to four cylinders forever.

Use engine configuration metadata:

{
  "engine_configuration": {
    "cylinder_count": 4
  }
}

The UI should render the configured number of cylinders.

This keeps the dashboard reusable for future engine configurations.

FOR EACH PARAMETER
------------------

Provide:

- Current value
- Unit
- Update/live status
- Normal/warning/critical state
- Threshold indication where appropriate
- Mini trend where useful
- Timestamp/data-age
- Source where useful

Avoid hardcoded telemetry inside components.

MVP VISUALIZATION

The virtual engine can be constructed from:

- Cylinders

- Torus geometry
- Lines/pipes
- Instanced geometry
- Other procedural Three.js objects

VISUAL STATES
-------------

NORMAL
- Stable engine animation
- Nominal indicators
- Normal subsystem states

OVERHEATING
- Thermal state visualization changes
- Temperature indicator rises
- Affected cylinder/region highlighted

MISFIRE
- Combustion animation becomes abnormal
- Affected cylinder highlighted
- Engine state changes
- Fault indicator appears

INJECTOR ABNORMALITY
- Fuel/injection subsystem highlighted
- Related diagnostic status shown
- Relevant cylinder may be highlighted when data supports it

LUBRICATION ISSUE
- Lubrication subsystem highlighted
- Oil condition displayed as degraded

ABNORMAL VIBRATION
- Engine vibration animation increases
- Vibration indicator changes

SENSOR DRIFT
- Sensor/channel indication shows abnormality
- Physical engine visualization must NOT falsely imply a physical engine
  change if only the sensor is faulty

STATE-DRIVEN DESIGN
-------------------

The 3D renderer should consume a normalized Twin visualization state:

{
  "engine_state": "DEGRADED",
  "health_index": 71,
  "rpm": 5200,
  "thermal_state": "ELEVATED",
  "combustion_state": "ABNORMAL",
  "lubrication_state": "NOMINAL",
  "vibration_state": "HIGH",
  "active_fault": "INJECTOR_ABNORMALITY"
}

The renderer maps state to visual behavior.

The renderer does NOT decide the diagnosis.

======================================================================
23. API CONTRACT RULES
======================================================================

1. API payloads must be versioned.
2. Field names must be stable.
3. Units must be explicit.
4. Timestamps must be machine-readable.
5. Arrays must have defined ordering.
6. Missing data must have defined representation.
7. Invalid data must not silently become zero.
8. Data source should be identifiable.
9. Schema changes require version updates when breaking.
10. Frontend must tolerate unavailable optional fields.
11. Backend validation is authoritative for incoming API data.
12. Frontend validation should protect rendering/runtime safety.

Recommended contract artifacts:

docs/
  specifications/
    telemetry.schema.json
    dashboard-api.yaml

The OpenAPI definition should be used to keep backend and frontend contracts
synchronized.

30. MOCK SCENARIO DATA REQUIREMENTS
======================================================================

NORMAL
------

- Stable RPM
- Stable MAP
- Balanced CHT
- Balanced EGT
- Normal oil pressure
- Normal oil temperature
- Normal fuel flow
- Normal vibration
- Healthy electrical system
- Healthy injection timing
- Health index near nominal

MISFIRE
-------

- Cylinder-specific combustion abnormality
- Corresponding CHT/EGT behavior
- RPM disturbance where appropriate
- Vibration change where appropriate
- Residual increase
- Diagnostic indication

INJECTOR ABNORMALITY
--------------------

- Cylinder-specific thermal/combustion deviation
- Relevant fuel/injection behavior
- Residual increase
- Diagnostic indication

LUBRICATION ISSUE
-----------------

- Oil pressure/temperature degradation
- Associated residuals
- Health degradation
- Maintenance advisory

OVERHEATING
-----------

- CHT/EGT elevation
- Thermal trend
- Health degradation
- Warning/critical alert depending on severity

SENSOR DRIFT
------------

- Sensor value becomes biased
- Physical engine state should remain logically distinct
- Sensor-health diagnostic should identify the channel
- 3D Twin should not falsely animate a physical fault

ABNORMAL VIBRATION
------------------

- Vibration increase/pattern change
- Potential supporting telemetry changes
- Health degradation
- Diagnostic indication

38. PERFORMANCE REQUIREMENTS
======================================================================

The dashboard should be designed for high-rate telemetry.

TARGETS
-------

Design for:

- Smooth chart updates
- Minimal unnecessary React re-renders
- Bounded in-memory buffers

- 3D update time
- End-to-end dashboard latency

Use profiling before optimizing.

39. PERFORMANCE MODULARITY
======================================================================

Keep high-rate data separate from low-rate UI state.

Example:

High-rate:
- Telemetry samples
- Chart buffers
- 3D animation state

Lower-rate:
- Fault classification
- Maintenance advisory
- Mission metadata
- Configuration
- Version information

Do not force the entire React application to re-render for every telemetry
sample.

Use bounded buffers and targeted subscriptions.

42. FAILURE / GRACEFUL DEGRADATION
======================================================================

The dashboard must remain usable when services fail.

EXAMPLES
--------

Backend unavailable:
- Show connection status
- Preserve available local UI
- Do not display stale data as current

AI unavailable:
- Telemetry remains available
- Twin analysis remains available if available
- AI section explicitly shows unavailable

Twin unavailable:
- Telemetry remains available
- Diagnostics remain available if available
- 3D Twin indicates unavailable

Data stale:
- Show age
- Do not pretend it is live

Invalid telemetry:
- Reject or quarantine invalid data
- Show validation state
- Do not silently convert invalid values to zero
